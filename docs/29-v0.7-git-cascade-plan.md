# v0.7 — git-cascade integration plan

Companion to [docs/25-team-orchestration.md §10.4](25-team-orchestration.md#104-git-cascade--branchpolicy-adapter-v07-q7) (architecture) and the v0.4/v0.5/v0.6 plan docs ([27](27-v0.4-teams-implementation-plan.md), [28](28-v0.5-daemon-plan.md)). This doc is the master execution plan for v0.7 — wiring git-cascade into swarm-harness so each team member can run inside its own git worktree on its own stream, with cascade-rebase on pipeline stage transitions.

## TL;DR

Add two `BranchPolicy` variants (`stream` / `fork`), a lazy-init `MultiAgentRepoTracker` adapter, worker-spawn cwd-into-worktree, `commitChanges` wiring on `CommitPolicy=auto`, pipeline cascade-rebase between stages, and default policies per topology from [§10.4](25-team-orchestration.md#104-git-cascade--branchpolicy-adapter-v07-q7). Worktree lifecycle binds to the worker FSM (created at spawn, deallocated at `exited`); orphans are reaped at orchestrator startup. Conflict policy is **`stop_on_conflict` + abort the lane** in v0.7 — agent-driven conflict resolution is deferred to v0.8. The reference integration (`claude-code-swarm`) is observation-only and gave us lifecycle patterns but no precedent for the generative flow; that flow is net-new design.

**Scope:** stages 7A–7E below. **Estimate:** ~6 days. **Acceptance:** §6.

---

## Why now

Today every team member spawned by [`TeamSession`](../src/swarm/team-session.ts) inherits the orchestrator's cwd. Two members editing the same files race. The v0.4 team primitives ([docs/27](27-v0.4-teams-implementation-plan.md)) shipped with `BranchPolicy = { none | reuse | create }` ([src/swarm/policies.ts:18](../src/swarm/policies.ts)), but `validateBranchPolicy` in [src/swarm/topologies/fanout.ts:707](../src/swarm/topologies/fanout.ts) explicitly defers git ops to "M3b" — branch policies are advisory only; no worktree, no commit driver, no merge.

git-cascade exists, ships a `MultiAgentRepoTracker` whose API matches the [§10.4](25-team-orchestration.md#104-git-cascade--branchpolicy-adapter-v07-q7) sketch verbatim, and emits MAP-shaped events out of the box. Wiring it closes the gap that's been open since v0.4 and unlocks pipelines-with-handoff (`stage-N reads stage-(N−1)'s commits`), which is the most-requested workflow not yet expressible in [docs/25 §8.2](25-team-orchestration.md#82-pipelinetopology).

What v0.7 doesn't add (deferred):

- **Agent-driven conflict resolution.** v0.7 uses `stop_on_conflict` only — when cascade rebase hits a real conflict, the lane aborts with a structured error. Agent-resolves-its-own-conflicts (the `onConflict: "agent"` codepath) is deferred to v0.8. Rationale: [docs/29 V0.7.Q5](#v07q5--conflict-policy).
- **Multi-team-in-one-orchestrator tracker scope.** v0.7 assumes one team per process (the v0.5 daemon shape). Tracker singleton lives on the team daemon. Multi-team-in-one-process is deferred to v0.8 per [docs/25 §6.4](25-team-orchestration.md#64-multi-team-in-one-orchestrator); when it lands, all teams in that process share one tracker.
- **`team merge` / aggregator stream merge.** [§10.4 "At team merge"](25-team-orchestration.md#104-git-cascade--branchpolicy-adapter-v07-q7) describes `tracker.mergeStream` at team completion. v0.7 ships the primitive (callable via `BranchPolicy=stream` + manual merge via CLI) but not the auto-aggregator. Aggregator merge is v0.8.
- **`stack` semantics.** git-cascade has a stack model (multi-stream dependency graphs). v0.7 uses linear streams only — pipeline-of-streams via `fork`. Stacks are v0.8+.
- **Worker re-attach with worktree adoption across orchestrator restarts.** v0.7's orphan-reaper deletes orphaned worktrees; it does not try to re-attach a fresh worker process to a dead worker's worktree. Adoption is v0.8 if a real workflow demands it.

## Reference survey — what we learned

Two reference repos were available (`macro-agent` is private/404):

1. **`git-cascade`** itself — public API surface verified. `MultiAgentRepoTracker` ([src/tracker.ts:124](https://github.com/alexngai/git-cascade/blob/main/src/tracker.ts#L124)) exposes every method named in [§10.4](25-team-orchestration.md#104-git-cascade--branchpolicy-adapter-v07-q7): `createStream`, `forkStream`, `mergeStream`, `syncWithParent`, `rebaseOntoStream`, `cascadeRebase`, `commitChanges`, `createWorktree`, `deallocateWorktree`, `listWorktrees`, `abandonStream`, `resolveConflict`. Storage is SQLite at `.git-cascade/tracker.db` (WAL mode, configurable path). Concurrency is optimistic — `stream_guards` table detects races after the fact rather than blocking. Recovery runs on tracker open. **API matches docs verbatim; no drift.**

2. **`claude-code-swarm`** (`cc-swarm`) — the only known reference integration. **Pure observer:** verified by grep, cc-swarm calls only `tracker.trackExistingBranch()`, `tracker.listStreams()`, `tracker.getStreamBranchName()`, and direct `tracker.db` reads (see [cc-swarm src/cascade-client.mjs](https://github.com/alexngai/claude-code-swarm/blob/main/src/cascade-client.mjs), `cascade-watcher.mjs`, `cascade-diff-server.mjs`). It never calls `createWorktree`, `createStream`, `forkStream`, `cascadeRebase`, or `commitChanges`. cc-swarm uses git-cascade to surface git activity that Claude Code does anyway (via its bash tool) as MAP events. That gives us **lifecycle patterns** (tracker open/close, lazy init, MAP event forwarding) but **no generative precedent.** v0.7 is operating the library in a mode no shipped consumer has exercised.

3. **What we borrow from cc-swarm:**
   - Tracker lifecycle pattern ([cc-swarm src/cascade-client.mjs](https://github.com/alexngai/claude-code-swarm/blob/main/src/cascade-client.mjs)) — initialize on first need, close on graceful shutdown, idempotent close.
   - `.git-cascade/tracker.db` storage location, no override.
   - MAP event forwarding — pass git-cascade's emitter through to our MAP adapter; events are already prefix-shaped (`x-cascade/stream.opened` etc.).

4. **What we have to invent (no precedent in cc-swarm):**
   - Spawn → worktree pairing (subprocess `cwd` override + tracker → worker FSM linkage).
   - Pipeline cascade trigger (PipelineTopology calls `cascadeRebase` between stages; library doesn't auto-trigger).
   - Conflict policy / lane abort path.
   - Worktree cleanup wired to worker FSM transitions.
   - Orphan reaper on orchestrator startup.

## Design lock — V0.7

Question numbers are v0.7-local. Carries forward decisions from [docs/25 §2](25-team-orchestration.md#2-decision-summary) and [§10.4](25-team-orchestration.md#104-git-cascade--branchpolicy-adapter-v07-q7). Twelve locks below; all resolved before stage 7A.

### V0.7.Q1 — Tracker singleton scope

**Decision:** one `MultiAgentRepoTracker` instance per team daemon process, lazy-initialized on the first task whose `branchPolicy.kind` is `stream` or `fork`. The tracker is held on `TeamSession` (lives for the daemon's lifetime); `close()` runs in the daemon's graceful-shutdown path before the socket unbinds.

Rejected: per-task tracker (re-opens SQLite every spawn — wasteful); host-wide singleton across multiple daemons (v0.5 chose per-team daemons, so this would force inter-process coordination that the optimistic-concurrency model isn't built for).

Multi-team-in-one-process (v0.8): when that lands, the tracker moves up to the orchestrator and is shared. Single tracker per repo is git-cascade's expected mode.

### V0.7.Q2 — When does the tracker materialize?

**Decision:** lazy. Daemon start does not open the tracker; the first task whose policy is `stream`/`fork` does. A team that never uses streams (e.g. all members on `kind: "none"`) pays zero cost — no `.git-cascade/` directory created.

Implication: `BranchPolicy=none|reuse|create` lanes never touch the tracker. v0.7 strictly extends the matrix; existing topologies keep working with no behavioral change.

### V0.7.Q3 — Worktree path scheme

**Decision:** `.git-cascade/worktrees/<agentId>/` relative to the repo root. `<agentId>` is the worker's stable ID from [src/swarm/worker-state-file.ts](../src/swarm/worker-state-file.ts). Always relative, never under `$TMPDIR` — keeps worktrees discoverable for the operator and aligned with git's expectation that worktrees can read repo config.

Rejected: `${XDG_RUNTIME_DIR}/swarm-harness/worktrees/...` — git worktree paths must be on the same filesystem as the repo for fast operations; XDG_RUNTIME_DIR often isn't. Rejected `<repo>/worktrees/<agentId>/` — would conflict with user-created directories.

### V0.7.Q4 — Stream → branch naming

**Decision:** use git-cascade's default — stream branches are `stream/<stream-id>`. Configurable via tracker `branchPrefix` but we won't expose that surface in v0.7. The stream ID itself is git-cascade's generated ULID-like value.

Operator-friendly display name comes from `CreateStreamOptions.name` — we set it to `<topology>/<memberRole>/<taskId>` (e.g. `pipeline/build/t-0042`) so `swarm-harness git-cascade list` reads naturally.

### V0.7.Q5 — Conflict policy

**Decision:** `stop_on_conflict` only in v0.7. When `cascadeRebase` returns `failed[]` non-empty, the topology emits a `cascade_conflict` lane event with the conflict descriptor and **aborts the lane** (pipeline) or **fails the task** (fanout). No agent prompt-loop, no auto-merge.

Rationale: agent-driven conflict resolution is a non-trivial design (which agent? what prompt? what budget?) and would gate v0.7. Ship the working path first.

Forward path (v0.8): introduce `BranchPolicy.conflictResolver?: { mode: "agent", role: string, budget }` — when set, on conflict the orchestrator spawns a new short-lived worker with that role and the conflict diff, and feeds its commit back to `resolveConflict`.

### V0.7.Q6 — Worktree cleanup lifecycle

**Decision:** worktree deallocation is bound to the worker FSM. `worker.transition('exited')` invokes `tracker.deallocateWorktree(agentId)` as part of cleanup. Drain (graceful) also deallocates after the in-flight task completes. Kill (signal) deallocates after the worker process is reaped.

Failure mode: if `deallocateWorktree` throws (e.g. directory busy on Windows; not currently in scope), the worker still transitions to `exited` but the worktree is flagged as orphaned and the orphan reaper (V0.7.Q11) handles it on next startup.

### V0.7.Q7 — Commit driver

**Decision:** when `commitPolicy.kind === "auto"` AND `branchPolicy.kind ∈ {"stream", "fork"}`, the commit action calls `tracker.commitChanges` instead of plain `git commit`. When `commitPolicy.kind === "auto"` AND `branchPolicy.kind ∈ {"none", "reuse", "create"}`, behavior is unchanged (plain git commit — same as today).

`commitChanges` adds `Change-Id` trailers and a row in the `changes` table; `git log --grep Change-Id` shows the full history for free.

### V0.7.Q8 — Pipeline cascade trigger

**Decision:** [`PipelineTopology`](../src/swarm/topologies/pipeline.ts) explicitly calls `tracker.cascadeRebase` between stages. Specifically: when stage N's task emits `task_result` and the policy is `stream`/`fork`, the topology calls `tracker.cascadeRebase({ from: <stage-N stream>, strategy: "stop_on_conflict" })` **before** dispatching stage N+1's task. If the cascade fails, stage N+1 is not dispatched; the lane aborts.

Rejected: library auto-cascade (git-cascade has no such mechanism; the lib emits events but doesn't trigger rebases from them). Rejected: watcher-based trigger à la cc-swarm — for a generative workflow we control, polling is unnecessary overhead.

### V0.7.Q9 — Defaults per topology

**Decision:** locked exactly as [§10.4 table](25-team-orchestration.md#104-git-cascade--branchpolicy-adapter-v07-q7):

| Topology | Default `defaultBranchPolicy` |
|---|---|
| Fanout | `{ kind: "stream" }` (each task = own stream) |
| Pipeline | stage 0: `{ kind: "stream" }`; stage N≥1: `{ kind: "fork", parentStreamId: <stage N−1's stream> }` |
| Coordinator | root: `{ kind: "stream" }`; spawned peers: `{ kind: "fork", parentStreamId: <root> }` |
| PeerTeam | `{ kind: "fork", parentStreamId: <team-base-stream> }` (team base stream created at team start) |
| Committee | `{ kind: "stream" }` per candidate |
| CriticLoop | executor: `{ kind: "stream" }`; critic: `{ kind: "none" }` (read-only) |

Spec-level `branchPolicy` overrides the topology default. Topology default applies only when the spec leaves `branchPolicy` undefined.

**Compatibility note:** today the default is `{ kind: "none" }`. Defaulting to `stream` in v0.7 is a behavioral change. To avoid surprising existing users, defaults activate **only when `--git-cascade` is passed** (mirrors `--map`). Without that flag, default stays `{ kind: "none" }`. See V0.7.Q10.

### V0.7.Q10 — Opt-in flag

**Decision:** new top-level CLI flag `--git-cascade` (and matching `gitCascade: true` in `TeamSpec` YAML). When set, the topology default branch policies from V0.7.Q9 activate; without it, default stays `{ kind: "none" }` and the tracker never opens.

Explicit `branchPolicy: { kind: "stream" }` on a spec works even without `--git-cascade` — the tracker opens lazily for that one task. The flag only governs *defaults*, not capability.

### V0.7.Q11 — Orphan reaper

**Decision:** team daemon startup (after tracker open) calls `tracker.listWorktrees()` and cross-references with worker state files in [`~/.swarm-harness/workers/`](../src/swarm/worker-state-file.ts). Any worktree whose `agentId` does not correspond to a live worker (PID alive AND state file `status` not `exited`) is deallocated.

Runs once at daemon start, before the first task dispatches. Logs each reap to `events.jsonl` as `cascade_worktree_reaped` with `{ agentId, path, reason }`.

### V0.7.Q12 — cc-swarm coexistence

**Decision:** if a user runs both cc-swarm and swarm-harness against the same repo, they share `.git-cascade/tracker.db` automatically — git-cascade's WAL mode supports concurrent readers, and the optimistic-concurrency guards detect any same-stream write race. Our streams are namespaced by name (`<topology>/<role>/<taskId>`) so collision is structurally improbable.

We do *not* attempt cross-tool stream affinity (e.g. swarm-harness reading streams created by cc-swarm). That's a v0.8+ federation question.

## Acceptance criteria (release gate)

A v0.7 release is gated on **all** of:

1. **Schema**: `BranchPolicySchema` accepts `{ kind: "stream", baseStreamId? }` and `{ kind: "fork", parentStreamId }`; rejects malformed shapes. Tested in [src/swarm/policies.test.ts](../src/swarm/policies.test.ts).
2. **Spawn**: a worker spawned with `branchPolicy.kind === "stream"` runs in a freshly created worktree under `.git-cascade/worktrees/<agentId>/`. `process.cwd()` of the worker is the worktree path.
3. **Commit**: with `commitPolicy.kind === "auto"`, the worker's commit lands as a `tracker.commitChanges` call — visible in `git log --grep Change-Id`.
4. **Cleanup**: on team end (or worker exit / drain / kill), the worktree directory is gone and `tracker.listWorktrees()` no longer returns it.
5. **Cascade**: a 3-stage pipeline with non-conflicting edits produces three commits in a linear chain (stage-2 ancestry contains stage-1's commit which contains stage-0's commit).
6. **Cascade conflict**: a 2-stage pipeline with a real conflict aborts cleanly — `cascade_conflict` event emitted, no stage-2 worker spawned, pipeline state is `failed`, tracker stream marked `conflicted`.
7. **Defaults**: `swarm-harness team start fanout-template --git-cascade` (with no `branchPolicy` in the template) produces per-task streams. Without `--git-cascade`, same template runs with `{ kind: "none" }` (today's behavior).
8. **Orphan reaper**: kill a worker process bypassing FSM; restart daemon with `--git-cascade`; the orphaned worktree is deallocated within 1s of daemon start.
9. **No regression**: all v0.4/v0.5/v0.6 tests pass with no behavioral change when `--git-cascade` is not passed.
10. **MAP forwarding**: with `--map --git-cascade`, MAP subscribers see `x-cascade/stream.opened`, `.committed`, `.merged`, `.conflicted` events for every lifecycle transition (no translation; pass-through).
11. **CLI surface**: `swarm-harness git-cascade list` returns the active team's streams. Output stable enough for scripting.
12. **Docs**: [docs/25 §10.4](25-team-orchestration.md#104-git-cascade--branchpolicy-adapter-v07-q7) updated; [README.md](../README.md) one-paragraph mention; CLAUDE.md operator section.

## Risks & mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| git-cascade API drift between survey and implementation start | Low | Medium | Re-verify against `package.json` resolved version at start of 7A. API is stable per docs ([§10.4](25-team-orchestration.md#104-git-cascade--branchpolicy-adapter-v07-q7) verified verbatim during this survey). |
| Worktree leak on daemon crash mid-spawn (worker started, FSM never reached `exited`) | Medium | Low | V0.7.Q11 orphan reaper on next daemon start. Operator can also run `swarm-harness git-cascade prune` (out of scope for v0.7 CLI — manual `tracker.deallocateWorktree` for now). |
| SQLite write contention if cc-swarm runs in same repo | Low | Low | git-cascade's WAL + optimistic guards handle concurrent readers; concurrent writes to the same stream are structurally improbable given naming scheme (V0.7.Q12). |
| Tests are slow due to real-git operations | Medium | Medium | Integration tests use in-tree fixture repos under `tmp/`. Unit tests for the adapter mock `MultiAgentRepoTracker`. CI runs both. |
| Conflict-on-cascade is more common than expected in real workflows | Medium | High (UX) | v0.7 aborts cleanly with a structured event — operator can manually resolve in the worktree and `tracker.resolveConflict`. Agent-resolves path is teed up for v0.8. |
| Worktree paths on case-insensitive filesystems (macOS default) collide for similar agent IDs | Low | Medium | agentId is a ULID; collisions on case-insensitive FS would require a collision in the ULID itself. |
| Tracker DB lock held across crash | Low | Low | git-cascade's `runRecoveryOnStartup` (default true) cleans stale locks. |

## Sequencing & parallelism

```
7A ──┬─→ 7B ──┬─→ 7C ──→ 7E
     │        └─→ 7D ──→ 7E
     └─→ (independent: docs sketches for §10.4 update can start here)
```

- **7A** unblocks everything; ~0.5d, single contributor.
- **7B and 7D defaults** are partially parallelizable after 7A: 7B does the heavy adapter work, 7D's default-policy resolver is independent. However 7D's orphan reaper depends on 7B's worker state file additions, so 7D is best sequenced after 7B.
- **7C** depends on 7B (needs the adapter + stream linkage between stages).
- **7E** depends on both 7C and 7D landing.

Practical sequence for one contributor: 7A → 7B → 7C → 7D → 7E. ~6 days.

Match the convention from [docs/27 §Tracking pattern](27-v0.4-teams-implementation-plan.md#tracking-pattern) and [docs/28 §Tracking pattern](28-v0.5-daemon-plan.md#tracking-pattern):

- Each stage gets a feature branch off the v0.7 base: `v0.7/7A-branch-policy-variants`, `v0.7/7B-cascade-adapter`, etc.
- PR title: `v0.7 stage 7A: <scope>`.
- Each PR self-contained — green tests, no leftover TODOs that block the next stage.
- Final integration PR (`v0.7/release`) merges all stages, runs full E2E, updates [docs/25 §13](25-team-orchestration.md#13-phased-delivery), tags `v0.7.0`.
