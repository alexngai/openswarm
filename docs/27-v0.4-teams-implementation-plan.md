## TL;DR

Ship the team orchestration layer. swarm-harness teams behave like Claude Code teams: peers in a team scope, lateral messaging, shared task graph, named topologies, persistent (long-lived) workers, MAP observability. Multi-engine peer parity — transport mode, `--framework claude-agent-sdk`, and `--framework codex-chatgpt` all serve as team peers via three different mechanisms that converge on the same `SwarmHost` semantics.

**Scope:** Stages 4A–4L below. **Estimate:** ~4 weeks. **Acceptance:** §6 below.

## Design lock — v0.4

Question numbers are v0.4-local. Carries forward decisions from [docs/25 §2](25-team-orchestration.md#2-decision-summary) plus the four pre-work locks (D4–D7) plus the three v0.4-spike-driven decisions (Q1, Q10, Q11).

### V0.4.Q1 — Coordinator topology depth model

**Decision:** flat siblings. All team members are at the same depth under the orchestrator (depth 1 if we count the orchestrator's `StandaloneHost` as depth 0).

`agent` tool input schema gains a `team?: "self" | "child"` parameter:

```ts
const inputSchema = z.object({
  prompt: z.string(),
  model: z.string().optional(),
  permissionMode: z.enum([...]).optional(),
  maxTurns: z.number().int().positive().optional(),
  wait: z.boolean().optional().default(true),
  team: z.enum(["self", "child"]).optional(),                // NEW v0.4
  framework: z.enum(["claude-agent-sdk", "codex-chatgpt"]).optional(),  // NEW v0.4 (Q9)
});
```

- `team: "self"` → spawn lands in caller's team scope as a peer. Used by `CoordinatorTopology` root.
- `team: "child"` → spawn lands as a sub-agent (today's tree semantics, depth+1, parent = caller). Default for non-coordinator contexts.
- Default depends on topology: `CoordinatorTopology` injects `"self"` via system-prompt + tool wrapping for the root; other contexts default to `"child"`.

### V0.4.Q2 — `peer-team` topology bootstrap

**Decision:** code-driven up-front spawn. Orchestrator reads spec, calls `team.spawnAll(specs)`, each member's prompt is the spec's prompt. Members learn about each other via:

1. System-prompt injection — "Your teammates: [{role, memberId}]". Static at spawn.
2. `team_members()` tool — runtime query, returns `[{memberId, role, agentId}]`. Refreshed on each call (handles member replacement).

Both. System-prompt for awareness; tool for fresh state.

### V0.4.Q3 — Long-lived worker failure / replacement policy

**Decision:** configurable per `coordination`, default replace-silently for `peer-team`/`committee`/`fanout`; default fail-team for `pipeline`/`coordinator`/`critic-loop` (replacement loses topology state).

### V0.4.Q4 — `team send <name> <prompt>` routing

**Decision:** configurable via `TeamSpec.entryPoint` field. Default per topology:
- `coordinator`/`critic-loop`/`pipeline` → root member.
- `fanout`/`peer-team`/`committee` → broadcast to `*`.

### V0.4.Q5 — Idle worker timeout

**Decision:** 10 minute default (`idleTimeoutMs: 600000`). Configurable per `TeamSpec.coordination.idleTimeoutMs`. On timeout, worker drains gracefully (finishes current then exits); orchestrator may respawn on demand.

### V0.4.Q6 — openteams library API additions

**Status:** external; CLI shell-out fallback for v0.4. File a separate openteams issue requesting:

1. `parseTemplate(path | name): Promise<TeamConfig>` — pure, in-process.
2. `materializeRolePrompts(config): Record<role, string>` — return strings, no disk write.
3. Stable types for `topology`, `communication`, `x-*` extension blocks.

**v0.4 ship path:** stage 4F wraps `openteams generate all` via subprocess. Adds ~50ms per team launch (acceptable; team launches are not hot path). Library-mode swap is a v0.5 follow-up.

### V0.4.Q7 — MAP scope conflicts

**Decision:** scope = `swarm:<teamName>:<orchestratorPid>` for default; users can override via `TeamSpec.coordination.mapScope` for explicit shared scopes (multi-orchestrator coordination scenarios).

### V0.4.Q8 — Codex as team substrate — RESOLVED via spike

Codex peers ship via Codex App Server's `DynamicToolCall` mechanism. See V0.4.Q11 for the tool subset registered. See [docs/26 §Track B](26-team-orchestration-spikes.md#track-b--codex-app-server-dynamictoolcall-viability) for the captured protocol trace.

### V0.4.Q9 — Mixed-engine consultant pattern

**Decision:** ship in v0.4 as a small additive surface. `agent` tool's `framework?` parameter (already shown in V0.4.Q1's input schema). The spawned child runs a framework-mode engine; orchestrator routes its output back as the `agent` tool's result. The child does NOT join the caller's team scope (it's a one-shot consultant, not a peer).

Use cases: cross-provider second opinion; specialty model routing; subscription-quota offload.

### V0.4.Q10 — Default peer-stop policy

**Decision:** team-scope-allowed peer-stop. `task_stop.ts` authorization rule:

```ts
async function canStop(caller: AgentInfo, target: TaskRecord, host: StandaloneHost): Promise<boolean> {
  // Team-scope shortcut: peers in the same team can stop each other.
  if (caller.scope === target.scope && caller.scope !== "swarm:default") {
    return true;
  }
  // Cross-scope: ancestry-check fallback (today's behavior).
  return host.isAncestorOf(caller.agentId, target.owner);
}
```

The `swarm:default` exclusion prevents the legacy single-team fanout from accidentally allowing cross-task-stop. Cross-team stop still requires ancestry (e.g., orchestrator can stop any team's task).

### V0.4.D4 — Scope-key migration

**Decision:** introduce `scope` dimension on `TaskRegistry` records, `RoleIndex` keys, and `StandaloneHost.agentToScope`. Implicit `"swarm:default"` scope for any agent not in a team. Migration sequence:

1. `TaskRegistry` — add `scope: string` field to `TaskRecord`, default `"swarm:default"`. Add optional `scope?` filter to `list`.
2. `RoleIndex` — composite key `${scope}/${role}`. All three methods (`register`, `agentsInRole`, `evict`) gain a `scope` parameter.
3. `StandaloneHost` — `agentToScope: Map<AgentId, string>` populated at spawn. `scopeOf(agentId)` lookup. `send()` scope-aware fan-out for `*` and `role:<x>`.
4. `TeamSession` — sets non-default scopes when registering members.

Existing tests pass without modification — they all use the implicit default scope.

### V0.4.D5 — `Orchestrator` → `Topology` refactor

**Decision:** thin `Orchestrator` shell + extracted `Topology` implementations under `src/swarm/topologies/`. `FanoutTopology` ports the existing fanout loop verbatim; new topologies are siblings.

Orchestrator entry points:
```ts
class Orchestrator {
  // LEGACY: synthesizes a Fanout TeamSpec internally; preserves today's `swarm run` UX.
  async run(tasks: TaskPacket[]): Promise<RunResult>;
  // NEW v0.4: direct topology entry.
  async runTeam(spec: TeamSpec): Promise<TeamResult>;
}
```

`TeamSession` owns: member registry, scope, branch-lock per member, stale-base check, lifecycle dispose. Topologies own: spawn/wait/retry/dead-letter logic specific to the shape.

### V0.4.D6 — IPC additions

**Decision:** four new request frames + four new task-registry frames + DynamicToolCall internal handler.

Long-lived worker:

| Frame | Direction | Purpose |
|---|---|---|
| `run_more` | orch → worker | Push new prompt to idle worker. Params: `{prompt, taskId?}`. Response: ack. |
| `drain` | orch → worker | Worker finishes current task then exits. Response: ack. |
| `worker_idle` | worker → orch (notification) | Worker awaiting next prompt. |
| `worker_drained` | worker → orch (notification) | Worker exited cleanly. |

Track A defect fixes:

| Frame | Purpose |
|---|---|
| `task.get` | Lookup `TaskRecord` by id. Closes Track A defect 1. |
| `task.list` | List with optional filter. |
| `task.create` | Create new task. |
| `task.update` | Patch existing task. |

Codex `DynamicToolCall` (in-process between `CodexAppServerProvider` and worker's `ToolDispatcher`):

- `CodexAppServerProvider` listens for `item/tool/call` JSON-RPC requests from Codex.
- Provider routes to `ToolDispatcher.dispatch(toolName, args, ctx)`.
- Provider formats result as `DynamicToolCallResponse{contentItems, success}` and replies.

`AgentHandle` API extensions:

```ts
interface AgentHandle {
  // existing
  wait(): Promise<AgentResult>;
  kill(): Promise<void>;
  events(): AsyncIterable<LaneEvent>;
  // NEW v0.4
  runMore(prompt: string, opts?: RunMoreOptions): Promise<AgentResult>;
  drain(): Promise<void>;
}
```

`SpawnRequest` extensions:

```ts
interface SpawnRequest {
  // existing
  task: TaskPacket;
  permissionMode: PermissionMode;
  // ...
  // NEW v0.4
  teamScope?: string;     // injected by TeamSession; defaults to "swarm:default"
  team?: "self" | "child";  // for `agent` tool spawns (per V0.4.Q1)
}
```

`worker_ready` notification payload gains `scope: string` (orchestrator records on registration).

### V0.4.D7 — Worker-host engine selection

**Decision:** unchanged structurally. Engine is per-worker, driven by `framework` env passed by orchestrator at spawn. Drop `framework-filter.ts` strip uniformly — Tier 2 tools are always present; outside a team scope they degrade gracefully (`send_message` returns `{delivered: 0}`, `check_inbox` returns `[]`, etc.).

### V0.4.D8 — Track A defect fixes (must ship in v0.4)

Three pre-existing defects surfaced by Track A. Each gets a stage entry (4I) and ships before v0.4 release:

1. **`task_output` broken for sub-agent workers** — fix via D6 (add `task.get`/`list`/`create`/`update` IPC handlers). The tool stays the same; the IPC layer gains the missing handlers.
2. **Dispatcher doesn't try/catch around `tool.execute()`** — wrap in `dispatcher.ts:156` to convert thrown exceptions to `{status: "error", message}`.
3. **`task_stop` self-stop transport race** — `WorkerTransport.kill()` defers child kill until after pending response writes have flushed.

## Acceptance criteria (release gate)

All of the following must hold before tagging `v0.4`:

1. **Multi-engine peer team works.** A `peer-team` of 3 members — one transport, one `--framework claude-agent-sdk`, one `--framework codex-chatgpt` — exchanges `send_message`s and shares `task_create`/`task_get` state. Output aggregates correctly. Recorded in a live smoke script.

2. **openteams template runs.** `swarm-harness team start gsd` runs the cc-swarm gsd template against swarm-harness's runtime. Topology resolution + per-role prompts materialized correctly.

3. **MAP observability matches cc-swarm.** With `--map ws://localhost:8080`, every `swarm.agent.spawned/completed`, `swarm.task.dispatched/completed`, `swarm.message.sent` event reaches a connected MAP observer with scope `swarm:<team>:<pid>`.

4. **Long-lived workers.** A `peer-team` worker runs 3 sequential prompts via `runMore` without respawning; idle timeout drains gracefully.

5. **Track A defects resolved.** `task_output` works for sub-agent workers; dispatcher returns structured error for thrown tools; self-stop doesn't hang.

6. **Track B fixture replays.** `test/fixtures/codex-app-server/dynamic-tool-call-spike.jsonl` replays cleanly as a passing test.

7. **Backward compat preserved.** `swarm run tasks.jsonl` produces byte-identical results.jsonl; existing single-agent CLI paths unchanged; `--framework claude-agent-sdk` and `--framework codex-chatgpt` single-agent runs work.

8. **Test posture.**

| Suite | Baseline (v0.3) | v0.4 target |
|---|---|---|
| `tsc --noEmit` | clean | clean |
| `npm test` | 1453 / 0 fail | ≥1700 / 0 fail |
| `bun test src/ui/repl-solid/` | 49 / 3 / 0 | 49 / 3 / 0 (no UI changes) |
| Live smoke | 5 categories | 7 categories (+ team, + codex-team) |

## Risks & mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| openteams CLI flag/format changes during v0.4 dev cycle | Med | Med | Pin the openteams version in package.json; document the dependency in stage 4F. |
| Codex App Server protocol changes `experimentalApi` shape | Low | High | Pin codex CLI version; capture additional protocol traces during stage 4H to detect regressions; v0.4 ships against `codex@0.98.0`. |
| `framework-filter` strip removal exposes a real failure case in single-agent claude-agent-sdk mode that Track A didn't cover | Low | Med | Stage 4G ports Track A tests + adds a single-agent regression test. |
| Long-lived worker memory/cache leaks across `runMore` calls | Med | Med | Stage 4D includes a 100-prompt stress test; observe RSS growth. |
| Scope-key migration breaks an obscure code path | Med | High | Audit every `RoleIndex` and `TaskRegistry` call site before merging stage 4A; keep implicit `swarm:default` semantically equivalent to today. |
| MAP server connection drops mid-team | Med | Low | Adapter implements connection retry with exponential backoff; lane events buffered briefly. (cc-swarm's sidecar handles this; we mirror.) |
| 4-week estimate slips | Med | Med | Stages 4A–4F are independent of MAP/openteams external work; can ship without 4F or 4J as v0.4-rc and add them in v0.4.1. |
