# v0.5 — Team daemon implementation plan

Companion to [docs/25-team-orchestration.md](25-team-orchestration.md) (architecture); the daemon was deferred from the v0.4 plan. This doc is the master execution plan for the v0.5 team daemon — the piece that flips `team send` / `list` / `stop` / `kill` from CLI stubs to working cross-process commands.

**Authoring date:** 2026-05-03.
**Status:** design lock.
**Supersedes:** the deferral notes for the long-lived team daemon. [docs/25 §17.2](25-team-orchestration.md#172-constrained--works-with-caveats) "team send/list/stop/kill are CLI stubs" limitation.
**Anchor:** [docs/00-vision.md](00-vision.md) — teams as services rather than batch jobs.

---

## TL;DR

Ship the long-lived team daemon. Per-team forked process per `team start --detach`. CLI commands `team send`, `team list`, `team stop`, `team kill`, `team logs` talk to a Unix socket per team under `${XDG_RUNTIME_DIR}/openswarm/teams/<name>/`. No crash recovery in v0.5 — `events.jsonl` is the forensic trail. Multi-engine peer parity, long-lived workers (4D), and the four shipped topologies are inherited unchanged from v0.4.

**Scope:** stages 5E.1–5E.7 below. **Estimate:** ~7.5 days. **Acceptance:** §6.

---

## Why now

[docs/25 §17.2](25-team-orchestration.md#172-constrained--works-with-caveats) documents the limitation: in v0.4, `team start` is synchronous and exits when the team finishes; `team send`/`list`/`stop`/`kill` are CLI stubs that print "deferred to v0.5+" and exit 2 ([src/cli/team.ts:321-351](../src/cli/team.ts)).

The daemon turns teams into services: `team start gsd --detach` returns immediately, the team keeps running, and a second shell can `team send gsd "review HEAD"` to push new prompts. Long-lived workers (shipped in 4D, [src/swarm/worker-lifecycle.ts](../src/swarm/worker-lifecycle.ts)) finally get exercised across shells.

## Design lock — V0.5 (daemon)

Question numbers are v0.5-daemon-local. Carries forward decisions from [docs/25 §2](25-team-orchestration.md#2-decision-summary) and the v0.4 design lock. Eight new locks below; all resolved before stage 5E.1.

### V0.5.Q1 — Daemon scope (per-team vs host)

**Decision:** per-team forked daemon. One OS process per running team. Each daemon hosts exactly one `TeamSession`.

Rejected alternatives:
- Single host daemon (multi-team-in-one-process) — would require multi-team `Orchestrator` first; bigger blast radius; closes [§docs/25 §6.4](25-team-orchestration.md#64-multi-team-in-one-orchestrator) prematurely.
- Hybrid (per-team daemon + shared `registry.jsonl`) — same architecture as per-team; the registry file is a cheap addition deferrable to v0.6 if `team list` directory walks feel slow.

Reversibility: per-team → host daemon is additive (the host can spawn per-team daemons). The reverse is harder. Locking per-team preserves both options.

### V0.5.Q2 — Default attachment behavior

**Decision:** `team start <template>` stays attached by default — preserves v0.4 byte-identical behavior. `--detach` is the new opt-in flag that double-forks the daemon and returns 0 once the socket is bound.

### V0.5.Q3 — Socket location

**Decision:** `${XDG_RUNTIME_DIR}/openswarm/teams/<name>/`. Files in that directory: `daemon.sock`, `daemon.pid`, `events.jsonl`, `team-state.json`.

On darwin where `XDG_RUNTIME_DIR` is unset, fall back to `${TMPDIR}/openswarm/teams/<name>/`. Project-local `.openswarm/` rejected — most use cases are user-global; project-scoped daemons can be added later via a `--scope project` flag if needed.

### V0.5.Q4 — Output streaming model

**Decision:** daemon writes `events.jsonl` (append-only, line-per-event). New `team logs <name>` subcommand reads it; `team logs <name> --follow` tails it via `fs.watch` + offset tracking. Mirrors `docker logs`. Avoids long-held streaming sockets.

Each line is one `LaneEvent` JSON-serialized + a top-level `ts` (ms epoch). Schema is the existing `LaneEvent` union from [src/swarm/events.ts](../src/swarm/events.ts) — no new types.

> **Phase 4.1d — `events.jsonl` is the blessed follow contract.** We deliberately did **not** add a `team_event` subscribe RPC over the daemon socket. `events.jsonl` is the official, stable contract for following a team:
> - **Format:** a wire-protocol JSONL stream ([src/swarm/wire-protocol.ts](../src/swarm/wire-protocol.ts)). Line 1 is a `_metadata` header (`protocol_version` + `producer: "team-daemon"`), written once on first open and not repeated on restart-append. Every subsequent line is a **recorded** `LaneEvent`; live-only high-frequency deltas (`text_delta` / `tool_use_input` / `heartbeat`) are filtered at write time and never appear. Truncated trailing lines (writer killed mid-write) are droppable; older-version records migrate forward through the wire registry.
> - **Consume it two ways:** humans tail raw bytes via `team logs <name> --follow`; programmatic consumers use `parseTeamEventsLog()` in [src/swarm/events-log.ts](../src/swarm/events-log.ts), which yields parsed, migrated `LaneEvent`s + a malformed-line count.
> - The `team_event` notification shape stays locked in the protocol only as a future **remote/hub** (MAP) wire; that path is threaded separately and does not use the daemon's Unix socket.

> **Phase 4.1 — daemon completion (status / drain / config).** Also landed alongside the events contract:
> - **`status`** now returns real per-member state (`spawning|running|idle|finished|failed`) read off the live `TeamSession`, whose `MemberInfo.state` is driven by host lane events (idle/exited/crashed/drained). Topologies that dispose after their run still report an empty member list.
> - **`stop`** performs a real graceful drain (Phase 4.1b): long-lived members get a cooperative `drain()`, one-shot members are awaited to completion, bounded by `StopParams.timeoutMs` (default 30s; `DEFAULT_DRAIN_TIMEOUT_MS`), then anything still live is force-killed. `kill` skips the drain (`drainTimeoutMs: 0`) and relies on process-exit reaping.
> - **`permissionMode` / `concurrency`** are no longer hardcoded (Phase 4.1c): threaded from `team start` via `OPENSWARM_DAEMON_PERMISSION_MODE` / `OPENSWARM_DAEMON_CONCURRENCY` (defaults `workspace-write` / `1`). The daemon writes a startup summary to `daemon.log`, warning up front when `spawn-resolver` conflict recovery is selected under a permission mode below `danger-full-access`.

### V0.5.Q5 — Crash recovery

**Decision:** none in v0.5. Daemon crash = team dead. Re-launching is the upgrade and recovery path. **(Superseded post-v0.5 by Crash-recovery T1 — auto-resume via `checkpoint.json`; see the Addendum below.)**

Reasoning: re-attaching to live worker subprocesses requires worker-side protocol changes (workers exit on stdin EOF today), daemon checkpointing of correlation tables + FSM state, and a re-handshake protocol — meaningfully larger than "ship a daemon." The only realistic value is bug-restart recovery, and `team start` again is bounded cost for typical minutes-hours team durations.

Sub-decisions:

| # | Question | Decision |
|---|---|---|
| **Q5a** | Worker death when daemon dies | Workers exit cleanly via stdin-close (today's behavior). No orphan reaper needed. Tested via `kill -9` of the daemon. |
| **Q5b** | Stale socket file cleanup | At `team start`, if `daemon.sock` exists but `kill -0 <pid>` fails, unlink the socket + pid file and proceed. |
| **Q5c** | `team list` for crashed teams | Filter out by default. `team list --all` (5E.4 stretch) shows crashed/completed entries. |
| **Q5d** | `events.jsonl` rotation | Punt to v0.6+. Document "rotate manually if it grows" for v0.5. |

Forward path if recovery becomes painful: v0.6+ adds `team-state.jsonl` checkpointing such that `team start --resume <name>` re-creates the team shape (members, roles, scope) with fresh worker subprocesses. Worker re-attach is a further v0.7+ option. Both are additive — locking "no recovery" in v0.5 doesn't paint into a corner.

### V0.5.Q6 — `team send` semantics

**Decision:** fire-and-forget. RPC returns when the message is enqueued in the team's inbox. Caller polls via `team logs --follow` for output.

At-least-once delivery: daemon flushes the inbox enqueue before sending the RPC reply. SIGTERM during enqueue may drop one in-flight message — documented.

**5F follow-up (shipped 2026-05-04):** the v0.5 daemon shipped with this RPC stubbed (returned an UNKNOWN_METHOD with a v0.6+ deferred-feature hint). 5F closes the deferral by adding `persistent` + `onTeamCreated` to TopologyContext, having PeerTeamTopology honor both, and routing send_prompt to `TeamSession.spawnMember` on the live session. The new ad-hoc member inherits role + policies from the spec's first member. Other topologies still dispose after their initial run; per-topology persistent opt-in lands when a real workflow surfaces. See [docs/25 §13 v0.6 row 5F](25-team-orchestration.md#13-phased-delivery) for the cross-link.

### V0.5.Q7 — Concurrent `team start` with same name

**Decision:** reject with `error: team "<name>" already running (pid X). Run 'team stop <name>' first.` Existing socket file + live pid is the lock. Stale-socket case (V0.5.Q5b) recovers transparently.

### V0.5.Q8 — Upgrade path

**Decision:** out of scope for v0.5. `team stop <name>` then `team start <name>` is the upgrade story. Document it.

Reasoning: hot-upgrade (binary swap with running workers) requires the same machinery as crash recovery — out of scope per Q5.

## Stage breakdown

7 stages, sequenced for protocol-then-daemon-then-CLI ordering. Each stage ends in a shippable, tested state. Stage commits follow the `v0.5 stage 5E.x: <summary>` pattern (mirrors v0.2/v0.3/v0.4).

Stage prefix is `5E` to avoid collision with `5D` (swarm watch TUI) and `5A`–`5C` already named in [docs/25 §13](25-team-orchestration.md#13-phased-delivery).

### Stage 5E.1 — Daemon protocol definition · ~0.5d

**Code:**
- New: `src/swarm/team-daemon-protocol.ts` — JSON-RPC frame shapes mirroring `src/swarm/ipc/protocol.ts`. Methods: `status`, `send_prompt`, `stop`, `kill`. Notifications: `team_event` (subscribe is deferred — v0.5 callers tail `events.jsonl` instead).
- New: zod schemas for each request / response.

**Tests:**
- New: `src/swarm/team-daemon-protocol.test.ts` (~80 LOC) — round-trip serialization + invalid-input rejection.

**Acceptance:** schema accepts well-formed RPCs; rejects malformed with clear errors.

### Stage 5E.2 — Daemon entry + double-fork · ~2d

**Code:**
- New: `src/swarm/team-daemon.ts` — daemon process entry. Construction: takes a `TeamSpec` + paths object (`{sockPath, pidPath, eventsPath, statePath}`); binds Unix socket; instantiates `Orchestrator` + `runTeam(spec)`; subscribes to lane events and appends each as a JSONL line. Signal handlers: SIGTERM/SIGINT → graceful drain (uses 4D `drain` IPC frame); SIGKILL handled by OS (workers exit on stdin EOF per V0.5.Q5a).
- New: `src/cli/team-daemon-entry.ts` — exec entry called by the parent forker. Reads spec from a temp file path passed in argv; calls into `team-daemon.ts`.

**Tests:**
- New: `src/swarm/team-daemon.test.ts` — fork lifecycle, socket cleanup on exit, signal handling. Uses a minimal in-process spec to avoid spawning real workers in the unit suite.

**Acceptance:** team-daemon process can be forked from a test harness, accepts a connection on its socket, exits cleanly on SIGTERM with `daemon.sock` and `daemon.pid` removed.

### Stage 5E.3 — `team start --detach` wiring · ~0.5d

**Code:**
- Modify: `src/cli/team.ts:runTeamStart` — new `--detach` branch. Serializes the resolved `TeamSpec` to a temp file; double-forks `team-daemon-entry.ts` with the temp file path in argv (via `child_process.spawn` with `detached: true, stdio: ['ignore', logFd, logFd]`). Parent retries `connect(socket)` for up to 2s (8 × 250ms) to confirm bind, then returns 0.
- Modify: `src/cli/argv.ts` — add `--detach` flag to `team start`.

**Tests:**
- Modify: `src/cli/team.test.ts` — assert `--detach` forks (use a stubbed forker); non-detach behavior byte-identical to v0.4 (regression test).

**Acceptance:** `openswarm team start gsd --detach` returns within 2s; daemon visible in `team list` (depends on 5E.4); existing non-detach path unchanged.

### Stage 5E.4 — `team send` / `list` / `stop` / `kill` RPC · ~1.5d

**Code:**
- Modify: `src/cli/team.ts` — replace `runTeamSend`/`List`/`Stop`/`Kill` stubs with real socket talk.
  - `team list` walks `${XDG_RUNTIME_DIR}/openswarm/teams/`, runs `kill -0 <pid>` per entry, returns live ones (V0.5.Q5c).
  - `team send` connects to socket; sends `send_prompt` RPC; returns ack.
  - `team stop` sends `stop` RPC (graceful drain via 4D `drain`); waits for daemon exit.
  - `team kill` sends `kill` RPC then SIGKILL after 5s timeout.

**Tests:**

**Acceptance:** end-to-end RPC against a running daemon for all four commands. Stale socket recovered. Duplicate `team start` rejected with clear error.

## Acceptance criteria (release gate)

All of the following must hold before tagging the daemon work as shipped:

1. **Backward compat preserved.** `openswarm team start gsd` (no `--detach`) byte-identical behavior to v0.4. Existing single-agent CLI paths unchanged. `swarm run tasks.jsonl` byte-identical results.jsonl as v0.4.

2. **Detach mode works.** `openswarm team start gsd --detach` returns within 2s; daemon visible in `team list`.

3. **Send delivers.** `team send gsd "prompt"` enqueues to the team entry point per V0.4.Q4 default (root for coordinator topologies; broadcast for peer-team).

4. **Stop drains gracefully.** `team stop gsd` uses the 4D `drain` IPC frame; daemon exits within ~30s of last in-flight task completing.

5. **Kill terminates fast.** `team kill gsd` terminates daemon + workers within 5s.

6. **List filters live.** `team list` shows live daemons only; stale (crashed) entries filtered (V0.5.Q5c).

7. **Logs read + follow.** `team logs gsd` reads up to last event; `--follow` streams live.

8. **Stale-socket recovery.** `team start gsd --detach` succeeds even if a previous daemon left a stale socket file (V0.5.Q5b).

9. **Duplicate rejection.** `team start gsd --detach` with a live `gsd` daemon errors with the V0.5.Q7 message.

10. **Worker cleanup on daemon SIGKILL.** `kill -9 <daemon-pid>` → worker subprocesses exit within 5s (V0.5.Q5a).

11. **Test posture.**

## Risks & mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Double-fork detach is platform-finicky | Med | Med | Use Node `child_process.spawn({detached: true})` + `unref()` pattern; CI tests on darwin + linux. |
| Worker subprocess orphans on daemon SIGKILL | Med | High | Workers exit on stdin EOF (today's behavior — V0.5.Q5a); explicit `kill -9` test in 5E.6. |
| Stale socket files block subsequent `team start` | High | Low | V0.5.Q5b cleanup; integration test in 5E.4. |
| `events.jsonl` unbounded growth in long teams | Low | Low | Document; manual rotation for v0.5; v0.6 considers built-in rotation. |
| Race: `team send` arrives before daemon socket binds | Med | Low | Bind-ack via 250ms × 8 = 2s retry loop in parent forker (5E.3). |
| CLI breaking change to existing `team start` (no `--detach`) | Low | High | 5E.3 keeps non-detach path byte-identical; regression test. |
| `XDG_RUNTIME_DIR` unset on darwin breaks defaults | Med | Med | `TMPDIR` fallback; documented; tested on darwin. |
| **Unix socket path > 104 chars (darwin)** | High | High | macOS silently truncates `<long-tmpdir>/.../daemon.sock` to `<...>/dae`, breaking client connect. **Discovered during 5E.6 smoke; fixed in 5E follow-up.** `src/cli/team-paths.ts` now computes the natural path and falls back to `/tmp/swh-<12-char-hash>.sock` (26 chars) when it would exceed 100 chars. Hash is derived from the natural path so the CLI client and daemon agree on the shortened location without out-of-band coordination. Smoke now exercises this fallback path with a long team name under `/var/folders/.../T/`. |
| Daemon SIGTERM during `send_prompt` loses message | Low | Low | Daemon flushes pending writes before exit; document at-least-once semantics in V0.5.Q6. |
| 7.5d estimate slips | Med | Med | 5E.3, 5E.4, 5E.5 are independent after 5E.2 ships; can ship 5E.4 first as `team-daemon-rc` and add 5E.5 later. |

## Addendum — Crash-recovery T1 (post-v0.5)

Realizes the forward path anticipated in V0.5.Q5: a durable per-team progress
checkpoint so a restarted daemon resumes mid-topology instead of re-running the
whole team. Auto-resume, no operator flag.

**Scope (T1):** skip units that already reached `succeeded`; re-run everything
else. No worker re-attach, no inbox snapshot (deferred to T2/T3).

**Artifact:** `checkpoint.json` in the team dir (alongside
`daemon.sock` / `daemon.pid` / `events.jsonl` / `state.json`), written via
atomic temp+rename on each unit completion.

**Generic interface (topology-agnostic):** `TeamCheckpointStore`
(`src/swarm/team-checkpoint.ts`) is injected onto `TopologyContext.checkpoint`.
Topologies opt in by calling `isDone(id)` / `get(id)` before dispatching a unit
and `record(unit)` after it reaches a terminal state. A topology that never
calls the store is simply not resumable yet — adoption is incremental. Wired in
T1: **fanout** (skip done tasks, replay stored result line) and **pipeline**
(skip done stages, thread the stored output forward). `peer-team`, `committee`,
`coordinator`, `critic-loop` keep the same hook and adopt later.

**Auto-resume safety:**
- `isDone` is true **only** for `succeeded` units — proven-good work is the only
  thing skipped; failed/timeout/cancelled units re-run.
- A `specHash` (topology + ordered members' id/role/prompt/model + completion
  rule) is stored; on open, a checkpoint whose hash doesn't match the current
  spec is discarded and a fresh run starts. Prevents auto-resume from stitching
  an edited team onto stale progress.
- Parallel `record()` calls (fanout) are serialized through an internal write
  chain so the file is never half-written.

**Wiring:** `computeTeamPaths` adds `checkpointPath`; `team start --detach`
exports `OPENSWARM_DAEMON_CHECKPOINT`; `TeamDaemon.start()` opens the store
before building the orchestrator (skipped for injected/test orchestrators) and
`stop()` flushes it. The orchestrator emits a `team_note` on resume.

**Deferred (at T1):** T2 — in-flight re-dispatch + worker engine-session
resume (now shipped, see below). T3 — inbox persistence + peer/emergent-topology
recovery (T3b peer-team + committee now shipped, see below; T3a inbox
persistence + coordinator/critic-loop still deferred).

## Addendum — Crash-recovery T2 (post-v0.5)

Extends T1 from "skip completed work" to "resume work that was mid-flight when
the daemon crashed." On restart, a unit that was dispatched but never reached a
terminal state is re-dispatched to a worker that (a) resumes its prior engine
session and (b) receives a verify-then-continue preamble.

**Checkpoint schema v2:** `checkpoint.json` gains an `inFlight[]` array of
`{ id, sidecarPath?, agentId?, dispatchedAt }`. `markDispatched(unit)` records a
unit as in-flight before spawn; the terminal `record(unit)` clears it. On open,
prior `inFlight` units that never reached `succeeded` become resume candidates
(`wasInFlight(id)`); `succeeded` always wins (a stale in-flight entry for a
completed unit is ignored). The schema bump discards v1 checkpoints (no
production data to migrate).

**Worker engine-session resume:** each dispatched unit gets a deterministic
per-unit session sidecar (`<teamDir>/sessions/<id>.session`) via the existing
`SpawnRequest.sessionSidecarPath` → `spawnWorker` plumbing (B1.4). The worker
now persists its engine session id to the sidecar **as soon as it's known**
(not just at turn end), so a mid-turn crash still leaves a resumable id. On
re-dispatch the worker reads the same sidecar and passes `resumeFrom`, continuing
its conversation instead of starting cold.

**Re-dispatch preamble:** in-flight re-dispatched units are prompted with a
"[Resumed after interruption] … verify current state, then continue, don't redo
completed steps" preamble (fanout `RESUME_PREAMBLE`). Per V0.5 review decision,
this fires for **all** in-flight members including those with commit/branch
policies — the preamble + worker verification is trusted rather than gating.

**Adoption:** fanout only in T2 (parallel work, highest value). Pipeline keeps
T1 behavior (skip succeeded stages); its stages are sequential so a crash loses
at most the current stage, which simply re-runs fresh. Other topologies unchanged.

**Verified live:** `scripts/smoke-team-checkpoint-resume-inflight.sh` — a real multi-process
daemon crashed WHILE a member was mid-flight (`kill -9`), restarted, re-dispatched
the member with the preamble, and the member resumed its prior scripted session
(`RESUMED:<sessionId>` observable in its recorded output).

## Addendum — Crash-recovery T3b (peer/emergent topologies)

Ports the T1+T2 recovery contract to the **batch-spawn** topologies —
`peer-team` and `committee`. fanout/pipeline own a per-task/-stage dispatch loop
and adopted the checkpoint directly; peer-team and committee instead spawn ALL
members in one `team.spawnAll(...)` and await a `CompletionRule` over the
handles, so they opt in through a shared helper rather than a rewrite.

**Shared helper** (`src/swarm/topologies/parallel-recovery.ts`):

- `planParallelDispatch(members, ctx, teamName, scope)` — per member, decides
  skip (a prior run recorded it `succeeded`) vs (re)spawn, layers the resume
  preamble + per-unit sidecar onto in-flight members, and `markDispatched`es
  each (re)spawned member. Pure pass-through when `ctx.checkpoint` is absent.
- `makeResolvedHandle(unitId, result)` — a synthetic already-resolved
  `AgentHandle` that stands in for a skipped member so the **existing**
  CompletionRule logic (`all`/`any`/`majority`/`deadline`/`until_signal`) counts
  it as complete with ZERO changes; index alignment with `spec.members` is
  preserved. `streamIdFor` returns undefined for its synthetic id, so
  stream-merge steps skip it.
- `recordTerminal(ctx, unitId, agentId, result)` — records a (re)spawned
  member's outcome. Called after the CompletionRule resolves (by then every
  spawned handle's memoized `wait()` has settled, killed losers included), so
  writes flush before a persistent team's daemon closes the store.

**Unit id:** `member.id ?? \`member-<idx>\``; positional ids are safe because
the checkpoint's spec-hash guard invalidates on any member-order/field change.

**Adoption:** peer-team + committee. Coordinator (dynamic peers, long-lived
root, no stable unit ids) and critic-loop (iteration cursor) are deferred.

**Scope limit (no inbox durability yet):** a re-dispatched member resumes its
OWN engine session (so it keeps messages it had already received), but messages
sent to it *after* the crash are not replayed — peer inbox persistence is T3a
(deferred). The verify-then-continue preamble mitigates the gap.

**Verified live:** `scripts/smoke-team-checkpoint-resume-parallel.sh` — a real multi-process
**peer-team** daemon crashed mid-flight (`kill -9`), restarted, re-dispatched
the member with the preamble, and the member resumed its prior scripted session
(`RESUMED:<sessionId>`).

**Deferred (remaining T3):** T3a — inbox/message persistence (memberId-keyed so
messages survive re-dispatch). Coordinator + critic-loop recovery.
